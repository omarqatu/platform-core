# The ten CI checks

PLATFORM_CORE v1.14 §3.6, numbered as the document numbers them. Built in T2 (PROOF_SPEC v1.1).

```bash
checks/core/run-checks.sh              # every check must return no violation (T2.1)
checks/core/run-checks.sh --self-test  # every check must fail on its planted violation (T2.2)
```

Each SQL check runs as `migrator` inside a transaction that is **always rolled back**. Checks 2
and 8 create reference policies under temporary names on the same table, and the self-test plants
its violation (`selftest/check-NN.*`) in that same transaction. Nothing persists. Checks 2 and 8
lock each table for the length of the check, so they run in CI and on test environments, never on
a live production database.

| Check | What it enforces | Input |
|---|---|---|
| 1 | Every table with `tenant_id` has RLS `ENABLE` + `FORCE` (the document's query) | — |
| 2 | The manifest: each table's policy set exactly, deparse against deparse (1.11); outside the manifest, the templates alone; the `NULLIF` rule on every policy (1.10) | `manifest.json` |
| 3 | The required core policies exist | `manifest.json` |
| 4 | No policy applies to PUBLIC (the document's query) | — |
| 5 | Every table in `public` has RLS `ENABLE` + `FORCE`, except the exemption file (the document's query) | `rls-exemptions.json` (empty) |
| 6 | Grants against the §3.8 matrix in both directions, with the columns, the database (CONNECT, TEMP), the schemas, executable routines, sequences, views, default privileges, and role memberships | `grants.json` |
| 7 | Every FK between two `tenant_id` tables is composite on `tenant_id` | — |
| 8 | `client_scope` on every table carrying `scope_ref_id` except `scope_assignments`, its inverse (1.14), and its text against the template | `manifest.json` (templates) |
| 9 | The second-axis variables appear in application code only in the declared writers (static) | `scope-variable-writers.json` (empty in T2) |
| 10 | Every table a policy expression reads (`pg_depend`, own table excluded) is a declared chain, each chain's inner table has its covering read policy, and no view or non-system function sits in a policy | `policy-chains.json` |

**The input files:**
- `manifest.json` is generated by extraction from the document: every `CREATE POLICY` on a
  concrete table, verbatim, plus the two templates of §3.1.
- `grants.json` and `policy-chains.json` state §3.8 and §4.6.
- A change to any of them is a change to what the document says, so it goes to the project owner.

The local repository check `check-schema-allowlist` lives in `checks/local/` and is not one of these
ten; it has a name, never a number.
