# Proposal for PLATFORM_CORE v1.16: managing members in the database

**Status:** the third draft, for the project owner, who writes v1.16. **Not built.** Nothing here enters `src/` or
`Migrations/` until v1.16 is issued.
**Base:** PLATFORM_CORE v1.15, PROOF_SPEC v1.2.
**Tested on:** PostgreSQL 18.6 (Debian 18.6-1.pgdg13+2), Npgsql.EntityFrameworkCore.PostgreSQL 10.0.3, .NET 10,
2026-09-25, in a separate probe database (`platform_probe`), migrated to v1.15 and seeded with the seed contract,
exactly as CI does, then with this draft applied as `migrator`.

## Changes since the second draft (owner's review)

1. **The old assignments are disabled at acceptance — D10, new.** The `provisioner` gets `SELECT` and
   `UPDATE (active)` on `scope_assignments`, with policies confined to a membership that is `left` and a
   `WITH CHECK` of `NOT active`; the step joins D9's order before re-activation, and a new chain enters Check 10.
   **Case: the member who returns sees no old assignment** (RT1: 0 active, committed and read from his own view).
2. **The old `membership_auth` row is reused** at re-activation — nothing inserted, nothing changed (RT3: 1 row).
3. **D8:** `USING (status = 'pending') WITH CHECK (status = 'revoked')`. **Case: a manager sets `accepted` →
   42501** (I11).
4. **New — items a and g cover disabling.** Disabling the last active owner, or the last active `all` member, is
   refused by the same lock and count. **Four new races** — a manager disables an owner while the other owner
   leaves, and three more — each ends with one left.
5. **New — the masking list in the audit log is declared:** `password_hash` and `token_hash`. **Case: creating an
   invitation → the audit row's `new_value` carries no `token_hash` value** (E7: `"token_hash": "[masked]"`).

> Everything in this draft is ready for v1.16's text. No open question remains from the second draft.

## Decisions settled by the project owner (for v1.16's text)

1. **F2 — `core.members.manage`**, granted to `owner` and `admin` through the templates. A new context variable,
   **`app.can_manage_members`**, is resolved in **step c** beside `app.can_manage_scope`. Its condition applies to:
   changing **another** member's status, writing `membership_roles`, creating invitations, and revoking them.
   **A member never changes their own roles** (`membership_id <> app.membership_id`). A hierarchy for granting
   roles (who may grant owner) is **deferred**.
2. **F1 — `membership_self_leave`:** `USING (status = 'active') WITH CHECK (status = 'left')`. The values are
   **`active` / `disabled` / `left`**. **`left` is final for a manager** (consent, 0): a manager moves a member
   between `active` and `disabled` only.
3. **Returning after leaving:** a new invitation; at acceptance the `provisioner` re-activates **the same row** —
   its roles and scope mode replaced by the invitation's, its old assignments disabled, its `membership_auth`
   reused.
4. **C1 — option ①:** lock the relevant **membership rows**, `ORDER BY id`, with **D7** (`membership_lock`) so that
   either manager can lock them — never the actor's own row through it, active rows only. **Items a and g cover
   departure, a role change, a downgrade, and disabling.**
5. **C2 — the self-service identity writes are exempt from automatic auditing, by a declared list;**
   `user_password_credentials` is **never** audited. **The masking list is declared:** `password_hash`,
   `token_hash`. A pre-launch item: auditing for identity.
6. **`ExecuteUpdate` / `ExecuteDelete` are forbidden by a static check**, except the password command.
7. **Bootstrap:** `POST /provision/tenants`, registered in **Development and CI only**.
8. **Acceptance with no account:** the token and a matching email are enough; **the token is single-use.**
9. **Invitations:** created `pending` only; revoked only with `core.members.manage`, only `pending` → `revoked`.

## How it was tested

- **The harness** (`cases.sh`): each case runs **alone**, as its role, with **only** the context it names, in a
  transaction that is **always rolled back**. The context values are the ones the resolution would produce for
  that member (a few cases set a synthetic combination, and say so). The result is `rows=N` (the command tag),
  `value=V` (the last SELECT), or `error=SQLSTATE`. **The expected result was written into each case before it
  ran,** and the harness compares.
- **Both directions:** every case runs against **v1.15** (the baseline — the cases that fail there are the gaps
  this draft closes) and against **the draft**, on a freshly migrated and seeded probe database.
- **Four case files:** `cases-v116.txt` (52: D1–D6, D8), `cases-d7.txt` (16: D7 and every combination its
  `USING` opens), `cases-rejoin.txt` (28: D9, D10; run with Khaled committed as `left` and Layla as `disabled`),
  and `cases-returned.txt` (6: after a **committed** rejoin of Khaled as the `provisioner`, read from Khaled's own
  view as `app_user`). The seed state is restored afterwards and checked.
- **The races** (`race2.sh`, `race3.sh`): two `app_user` transactions at once, each holding its locks for 2 s
  before committing; the count that decides is a **separate statement after the lock** (READ COMMITTED gives it a
  fresh snapshot). Setup and reset as `migrator`; the seed restored afterwards and checked. `race3.sh` also runs
  with **no lock taken**, the baseline.
- **Through EF** (the `t4ef` probe, on the draft): the §7 mechanism with the declared exemption and masking lists,
  the full bootstrap and an acceptance through the real EF commands, and an invitation created as `app_user`.

### D3. `membership_tenant_update` — another member's status (replaces the v1.15 text)

```sql
CREATE POLICY membership_tenant_update ON memberships
  FOR UPDATE TO app_user
  USING (
    tenant_id = (SELECT NULLIF(current_setting('app.tenant_id', true), '')::uuid)
    AND COALESCE((SELECT NULLIF(current_setting('app.can_manage_members', true), '')::boolean), false)
    AND id <> (SELECT NULLIF(current_setting('app.membership_id', true), '')::uuid)
    AND status IN ('active', 'disabled'))
  WITH CHECK (
    tenant_id = (SELECT NULLIF(current_setting('app.tenant_id', true), '')::uuid)
    AND COALESCE((SELECT NULLIF(current_setting('app.can_manage_members', true), '')::boolean), false)
    AND id <> (SELECT NULLIF(current_setting('app.membership_id', true), '')::uuid)
    AND status IN ('active', 'disabled'));
```

**A rule for every UPDATE policy on this table (proven by running it):** PostgreSQL combines permissive UPDATE
policies per phase — a row may pass `USING` through one policy and the new row `WITH CHECK` through another. So a
condition on the **old** state (here: not `left`) holds only if **every** UPDATE policy's `USING` carries it, and
the actor's own conditions must sit in `WITH CHECK` as well as `USING`. D3, D4 and D7 are written that way; the
M, X and RJ cases run every combination.

### D7. `membership_lock` — the rows items a and g lock, for either manager (new)

```sql
CREATE POLICY membership_lock ON memberships
  FOR UPDATE TO app_user
  USING (
    tenant_id = (SELECT NULLIF(current_setting('app.tenant_id', true), '')::uuid)
    AND id <> (SELECT NULLIF(current_setting('app.membership_id', true), '')::uuid)
    AND status = 'active'
    AND (COALESCE((SELECT NULLIF(current_setting('app.can_manage_members', true), '')::boolean), false)
         OR COALESCE((SELECT NULLIF(current_setting('app.can_manage_scope', true), '')::boolean), false)))
  WITH CHECK (false);   -- a row lock (FOR UPDATE), never a write
```

**Why it exists:** with D3, locking another member's row takes `core.members.manage`. Item g's actor holds
`core.scope.manage`; without the members permission, `FOR UPDATE` over the `all` members' rows locked **none of
them, with no error** (first draft: Rami locked 0 of 3), the other downgrade did not wait, and both succeeded →
**0 `all`**.
**Each condition is load-bearing:** `WITH CHECK (false)` — it never passes, so every write still needs D3's or
D4's `WITH CHECK`. `id <> app.membership_id` — the actor's own row is lockable only through D4, i.e. only while
`active` (an escape from disabling closed: X8, X13). `status = 'active'` — without it, this `USING` combined with
D3's `WITH CHECK` brought a `left` member back (M12, M15, RJ18 were 1 row until it was added). The lock sets of a
and g are active rows, so it costs nothing.
**What it changes:** a manager's write that no policy permits, on an active row, is refused **loudly** (42501)
rather than silently (0 rows) — M3.

### The locks for items a and g (option ①), as v1.16 would state them

```
a. The last active owner — for a departure, removing an owner role, or disabling an owner:
   SELECT m.id FROM memberships m
    WHERE m.tenant_id = app.tenant_id AND m.status = 'active'
      AND EXISTS (owner role, is_system)
    ORDER BY m.id FOR UPDATE OF m;
   then, in a separate statement, count the active owners; refuse if the change leaves none.
g. The last active `all` membership — for a downgrade, or disabling an `all` member:
   the same over the active memberships whose membership_scope is 'all';
   then count them in a separate statement; refuse if the change leaves none.
Never lock membership_scope rows for this: membership_scope_admin_update excludes the actor's
own row, so the lock silently skips it (run on v1.15: the race still leaves 0 `all`).
```

**A binding code rule (proven by the races):** lock first, in its own statement, `ORDER BY id`; then count **in a
separate statement** — under READ COMMITTED it takes a fresh snapshot after the lock is granted and sees the
other transaction's committed change. The lock statement's own subquery is **not** re-checked after the wait: a
guard comparing "rows locked" with a count taken after the lock reports a false mismatch under contention (the
race's run: "locked 2 of 1"). With D7 no such guard is needed for correctness; if one is kept, its count must be
taken before the lock.

### D9. Rejoining by a new invitation — the `provisioner` re-activates the same row (new)

**Why the same row:** `UNIQUE (tenant_id, user_id)` on `memberships` and `UNIQUE (tenant_id, membership_id)` on
`membership_scope` allow no second one (RJ16: 23505). **Why the roles and the mode are replaced:** a member's
role links survive their departure; re-activation that only inserts the invitation's role would bring the old
roles back with it (RJ6: 2 role links — the old `operator` beside the invited `viewer`). **`membership_auth` is
reused:** the existing row stays as it is (the acceptance provider is fixed to `'password'`, item c); nothing is
inserted (RT3: 1 row after rejoining).

```sql
-- The grants (3.8) — additions for provisioner:
GRANT UPDATE (status) ON memberships TO provisioner;
GRANT SELECT, DELETE ON membership_roles TO provisioner;
GRANT SELECT, UPDATE (scope_mode) ON membership_scope TO provisioner;

-- Only 'left' → 'active' — never 'disabled' (no escape from disabling), only in app.tenant_id (4.4).
CREATE POLICY memberships_provisioner_rejoin ON memberships
  FOR UPDATE TO provisioner
  USING (
    tenant_id = (SELECT NULLIF(current_setting('app.tenant_id', true), '')::uuid)
    AND status = 'left')
  WITH CHECK (
    tenant_id = (SELECT NULLIF(current_setting('app.tenant_id', true), '')::uuid)
    AND status = 'active');

-- The old roles and the old mode, of a member who left — and of no one else.
-- (SELECT is needed because DELETE/UPDATE with a WHERE read the rows: privileges and SELECT policies, 3.8.)
CREATE POLICY membership_roles_provisioner_select ON membership_roles
  FOR SELECT TO provisioner
  USING (
    tenant_id = (SELECT NULLIF(current_setting('app.tenant_id', true), '')::uuid)
    AND EXISTS (SELECT 1 FROM memberships m
```

still being `left`):

## The other decisions, as document text (no SQL)

- **C2 — automatic auditing (§7), with two declared lists:**
  - **The exemption list:** the self-service identity writes — `users (last_login_at, language, theme)` under
    `user_self_update` — are not audited automatically; `user_password_credentials` is **never** audited (its only
    change is the password command). `auth_attempts` is its own log. **Pre-launch item:** auditing for identity.
  - **The masking list:** `password_hash`, `token_hash` — the column stays in `old_value` / `new_value`, its value
    is replaced by `"[masked]"` and never enters the log.
  - Every other write is audited in its own transaction, by the §7 mechanism: capture at `SavingChanges`, a second
    save of the audit rows from `SavedChanges`, a flag against auditing the audit (run through EF: E1, E2, E4, E5,
    E7).
- **The static check:** `ExecuteUpdate` / `ExecuteDelete` appear nowhere in application code, except the password
  command — a bulk command bypasses the change tracker, so the audit interceptor never sees it (E3: 1 row updated,
  0 audit rows). A named local check beside `check-schema-allowlist`, with a self-test on a plant.
- **Bootstrap:** `POST /provision/tenants`, registered in Development and CI only — Api refuses to register it in
  any other environment (the pattern of the migrator guard and of `Session:RequireHttps`).
- **Acceptance with no account:** the token and an email matching the invitation's are enough; the person, user
  and credential are created in the acceptance transaction. **Single-use:** the invitation's update is
  `status = 'accepted' WHERE status = 'pending'`, a critical write expecting one row (run: 1, then 0 on a second
  try).
- **Acceptance for someone who left:** the order of D9 and D10 above. For someone `disabled` or `active` in that
  tenant, acceptance is refused.
