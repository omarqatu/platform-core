# Proposal for PLATFORM_CORE v1.16: managing members in the database

**Status:** a draft for the project owner, who writes v1.16. **Not built.** Nothing here enters `src/` or
`Migrations/` until v1.16 is issued.
**Base:** PLATFORM_CORE v1.15, PROOF_SPEC v1.2.
**Tested on:** PostgreSQL 18.6 (Debian 18.6-1.pgdg13+2), 2026-09-25, in a separate probe database
(`platform_probe`), migrated to v1.15 and seeded with the seed contract, exactly as CI does.

> **One point needs your decision before v1.16 (D7):** with option ① as decided, a scope manager who does not
> hold `core.members.manage` **cannot lock** the membership rows that item g's lock needs, and the lock
> silently locks nothing. The race then leaves **zero `all` memberships**. D7 below closes it with a lock-only
> policy; the alternative is a guard in the code that refuses such downgrades loudly. Both were run.

## Why: what the T4 rule-11 run found (v1.15)

| Finding | Reproduction on v1.15 |
|---|---|
| **F1** A member disabled by an admin re-enables themselves | Sara disables Khaled (UPDATE 1); Khaled, with `app.user_id` alone, sets his own status to `active` → **UPDATE 1**. `membership_self_leave` checks only `user_id`. |
| **F2** Managing members is application-only, and there is no permission to check | Khaled (operator) disables Omar (owner) → **UPDATE 1**; deletes Omar's owner role → **DELETE 1**; grants himself owner → **INSERT 1**. Layla (viewer) invites anyone with any role, owner included → **INSERT 1**. The catalog holds only `core.scope.manage`. |
| **C1** The tenant-row lock (spec items a, g) cannot be taken by `app_user` | `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE` on `tenants` → **42501** each: the matrix gives `app_user` SELECT only. A column grant with no UPDATE policy locks **0 rows, silently**. Without a lock, two owners leaving at once → **0 owners**; two downgrades at once → **0 `all`**. |
| **C2** Automatic auditing (§7) cannot audit a write with no tenant | Login's `last_login_at`, audited automatically → **42501** on `audit_log` (its `tenant_id` is NOT NULL, its policy needs `app.tenant_id`). |

## Decisions settled by the project owner (for v1.16's text)

1. **F2 — `core.members.manage`**, granted to `owner` and `admin` through the templates. A new context variable,
   **`app.can_manage_members`**, is resolved in **step c** beside `app.can_manage_scope`. Its condition applies to:
   changing **another** member's status, writing `membership_roles`, and creating invitations. **A member never
   changes their own roles** (`membership_id <> app.membership_id`). A hierarchy for granting roles (who may grant
   owner) is **deferred**.
2. **F1 — `membership_self_leave`:** `USING (status = 'active') WITH CHECK (status = 'left')`. The values are
   **`active` / `disabled` / `left`**.
3. **C1 — option ①:** lock the relevant **membership rows**, `ORDER BY id`.
4. **C2 — the self-service identity writes are exempt from automatic auditing, by a declared list;**
   `user_password_credentials` is **never** audited. A pre-launch item: auditing for identity.
5. **`ExecuteUpdate` / `ExecuteDelete` are forbidden by a static check**, except the password command.
6. **Bootstrap:** `POST /provision/tenants`, registered in **Development and CI only**.
7. **Acceptance with no account:** the token and a matching email are enough; **the token is single-use.**

## How it was tested

- **The harness** (`cases.sh`): each case runs **alone**, as its role, with **only** the context it names, in a
  transaction that is **always rolled back**. The context values are the ones the resolution would produce for
  that member (a few cases set a synthetic combination, and say so). The result is `rows=N` (the command tag),
  `value=V` (the last SELECT), or `error=SQLSTATE`. **The expected result was written into each case before it
  ran,** and the harness compares.
- **Three runs of the same 44 cases:** against v1.15 (the baseline: the cases that fail are the gaps), against
  the draft D1–D6, and against D1–D7, plus ten cases for D7's combinations.
- **The races** (`race2.sh`): two `app_user` transactions at once, each holding its locks for 2 s before
  committing; the count that decides is a **separate statement after the lock** (READ COMMITTED gives it a
  fresh snapshot). Setup and reset as `migrator`; the seed restored afterwards and checked.

## The proposed texts

### D1. The permission, and its templates (data, seeded by `migrator`)

```sql
INSERT INTO permissions (id, module_id, code, name_ar, name_en)
SELECT uuidv7(), p.module_id, 'core.members.manage', 'إدارة الأعضاء', 'Manage members'
FROM permissions p WHERE p.code = 'core.scope.manage';

INSERT INTO role_template_permissions (template_id, permission_id)
SELECT t.id, p.id FROM role_templates t CROSS JOIN permissions p
WHERE t.code IN ('owner', 'admin') AND p.code = 'core.members.manage';

-- Existing tenants' system roles are upgraded from the templates by migrator (one source of truth, 5).
INSERT INTO role_permissions (id, tenant_id, role_id, permission_id)
SELECT uuidv7(), r.tenant_id, r.id, rtp.permission_id
FROM roles r
JOIN role_templates t ON t.code = r.code AND r.is_system
JOIN role_template_permissions rtp ON rtp.template_id = t.id
JOIN permissions p ON p.id = rtp.permission_id AND p.code = 'core.members.manage';
```

**The resolution, step c (3.5/6)** — one read, both permissions, then two `SET LOCAL` in this order:

```
c. membership_roles → role_permissions → permissions
   → SET LOCAL app.can_manage_scope    (core.scope.manage)
   → SET LOCAL app.can_manage_members  (core.members.manage)
```

The system context and background jobs (8): `app.can_manage_members = false`, like `app.can_manage_scope`.
Every read of it is `COALESCE((SELECT NULLIF(current_setting('app.can_manage_members', true), '')::boolean), false)`
(the 1.10 rule; Check 2 enforces it).

| R1 | the templates carrying the permission | 2 (owner, admin) | 2 ✅ |
| R2–R6 | step c for Sara / Omar / Rami / Khaled / Layla → (scope, members) | t,t / t,t / t,f / f,f / f,f | as expected ✅ |

### D3. `membership_tenant_update` — another member's status (replaces the v1.15 text)

```sql
CREATE POLICY membership_tenant_update ON memberships
  FOR UPDATE TO app_user
  USING (
    tenant_id = (SELECT NULLIF(current_setting('app.tenant_id', true), '')::uuid)
    AND COALESCE((SELECT NULLIF(current_setting('app.can_manage_members', true), '')::boolean), false)
    AND id <> (SELECT NULLIF(current_setting('app.membership_id', true), '')::uuid))
  WITH CHECK (
    tenant_id = (SELECT NULLIF(current_setting('app.tenant_id', true), '')::uuid)
    AND COALESCE((SELECT NULLIF(current_setting('app.can_manage_members', true), '')::boolean), false)
    AND id <> (SELECT NULLIF(current_setting('app.membership_id', true), '')::uuid)
    AND status IN ('active', 'disabled'));
```

**Why the conditions sit in `WITH CHECK` too:** PostgreSQL combines permissive UPDATE policies per phase — a row
may pass `USING` through one policy and `WITH CHECK` through another. With the member's own conditions in both
clauses of every UPDATE policy on the table, no combination opens a transition that no single policy allows
(the M and X cases run every combination).

### D4. `membership_self_leave` — departure only (replaces the v1.15 text; F1)

```sql
CREATE POLICY membership_self_leave ON memberships
  FOR UPDATE TO app_user
  USING (
    user_id = (SELECT NULLIF(current_setting('app.user_id', true), '')::uuid)
    AND status = 'active')
  WITH CHECK (
    user_id = (SELECT NULLIF(current_setting('app.user_id', true), '')::uuid)
    AND status = 'left');
```

### D7 (proposed — your decision). `membership_lock` — the rows item g locks, for either manager

**The finding (L3, and the race "g, Rami"):** with D3, locking another member's row takes
`core.members.manage`. Item g's actor holds `core.scope.manage`; if they do not also hold the members permission,
`FOR UPDATE` over the `all` members' rows locks **none of them, with no error** (Rami: locked 0 of 3), the other
downgrade does not wait, and both succeed → **0 `all`**.

```sql
CREATE POLICY membership_lock ON memberships
  FOR UPDATE TO app_user
  USING (
    tenant_id = (SELECT NULLIF(current_setting('app.tenant_id', true), '')::uuid)
    AND (COALESCE((SELECT NULLIF(current_setting('app.can_manage_members', true), '')::boolean), false)
         OR COALESCE((SELECT NULLIF(current_setting('app.can_manage_scope', true), '')::boolean), false)))
  WITH CHECK (false);   -- a row lock (FOR UPDATE), never a write
```

**It opens no write:** its `WITH CHECK (false)` never passes, and every write still needs the `WITH CHECK` of D3
or D4 (both carry the actor's own conditions). What it changes: a manager's write that no policy permits is now
refused **loudly** (42501) rather than silently (0 rows) — M3 and M14 above.

| X9 | Rami, disabled, re-enables himself | 42501 | 42501 ✅ |
| X10 | Omar locks Maan's rows | 1 (his own Maan membership, through D4) | 1 ✅ |

**The alternative without D7 — a guard in the code:** refuse the downgrade loudly when fewer rows were locked
than are visible (race "g, Rami, with a code guard": Rami refused, 1 `all` left). It keeps the rule, at a price: a
scope manager without `core.members.manage` can then never downgrade an `all` member. **Found while running it:**
the guard's count must be taken **before** the lock waits — after the wait, the lock statement's subquery is not
re-checked (the race's run under D7 showed "locked 2 of 1"). With D7 the guard is not needed for correctness.

**A binding code rule either way (proven by the races):** lock first, in its own statement, `ORDER BY id`; then
count **in a separate statement** — under READ COMMITTED it takes a fresh snapshot after the lock is granted, and
sees the other transaction's committed change.

## The locks for items a and g (option ①), as v1.16 would state them

```
a. The last owner (departure, or removing an owner role):
   SELECT m.id FROM memberships m
    WHERE m.tenant_id = app.tenant_id AND m.status = 'active'
      AND EXISTS (owner role, is_system)
    ORDER BY m.id FOR UPDATE OF m;
   then, in a separate statement, count the active owners; refuse if the change leaves none.
g. The last `all` membership (a downgrade):
   the same over the active memberships whose membership_scope is 'all';
   then count them in a separate statement; refuse if the downgrade leaves none.
Never lock membership_scope rows for this: membership_scope_admin_update excludes the actor's
own row, so the lock silently skips it (run on v1.15: the race still leaves 0 `all`).
```

## The other decisions, as document text (no SQL)

- **C2 — the declared exemption list for automatic auditing (§7):** the self-service identity writes —
  `users (last_login_at, language, theme)` under `user_self_update` — are not audited automatically;
  `user_password_credentials` is **never** audited (its only change is the password command). `auth_attempts`
  is its own log. Every other write is audited in its own transaction, by the §7 mechanism (run: a second save
  from `SavedChanges`, the same transaction, no audit of the audit, rolled back together). Secrets are masked in
  `old_value` / `new_value` (run: an unmasked bootstrap put `password_hash` in `new_value`). **Pre-launch item:**
  auditing for identity.
- **The static check:** `ExecuteUpdate` / `ExecuteDelete` appear nowhere in application code, except the password
  command — a bulk command bypasses the change tracker, so the audit interceptor never sees it (run: 1 row
  updated, 0 audit rows). A named local check beside `check-schema-allowlist`, with a self-test on a plant.
- **Bootstrap:** `POST /provision/tenants`, registered in Development and CI only — Api refuses to register it in
  any other environment (the pattern of the migrator guard and of `Session:RequireHttps`).
- **Acceptance with no account:** the token and an email matching the invitation's are enough; the person, user
  and credential are created in the acceptance transaction. **Single-use:** the invitation's update is
  `status = 'accepted' WHERE status = 'pending'`, a critical write expecting one row (run: 1, then 0 on a second
  try).

## What changes elsewhere (for v1.16 and its implementation)

- **The manifest:** `memberships` — `membership_tenant_update` and `membership_self_leave` restated, and
  `membership_lock` if D7 is adopted; `membership_roles` — the two restrictive policies; `invitations` —
  `invitations_insert` restated. Check 3's required set grows with them.
- **Check 9:** `app.can_manage_members` joins the second-axis variables; the resolver stays its only writer.
- **Test 27:** six context variables, not five.
- **Grants:** none change. `memberships` keeps UPDATE (status); `membership_roles` SELECT, INSERT, DELETE;
  `invitations` SELECT, INSERT, UPDATE (status).
- **Deferred (your decision):** the hierarchy of granting roles — under this text an admin can grant `owner`.

## Open questions

1. **D7:** adopt `membership_lock`, or the code guard (scope managers without the members permission cannot
   downgrade)?
2. **M12:** may a manager re-activate a member who **left** (`left` → `active`)? D3 allows it. Related: a member
   who left cannot be invited back through acceptance — `UNIQUE (tenant_id, user_id)` rejects a second membership
   (run in T4's rule 11: 23505) — so re-joining is either this re-activation or acceptance re-activating the old row.
3. **I7:** revoking an invitation (`invitations_tenant_update`) is still open to any member. Gate it with
   `core.members.manage` like creating one?
4. **Invitation status at creation:** `invitations_insert` accepts any `status`, `accepted` included (run in T4's
   rule 11: INSERT 1). Harmless to acceptance (it requires `pending`), but add `AND status = 'pending'`?
5. **X8:** a disabled scope manager, with the tenant context set **by hand**, can mark themselves `left`
   (`disabled` → `left`). Not reachable through the application — the resolution refuses a membership that is not
   active — but it is a transition no single policy intends. Acceptable, or narrow D4's `WITH CHECK` further?
