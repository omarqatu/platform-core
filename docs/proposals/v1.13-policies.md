# Proposal for PLATFORM_CORE v1.13: the missing policy texts

**Status:** a draft for the project owner's review. **Not built.** Nothing here
enters `src/` or `Migrations/` until v1.13 is issued.
**Base:** PLATFORM_CORE v1.12, PROOF_SPEC v1.1.
**Tested on:** PostgreSQL 18.6 (Debian 18.6-1.pgdg13+2), 2026-09-24.

## Why this exists

v1.12 writes 22 policies in full, plus the two templates. But in the 3.8 matrix,
each grant to a role other than `migrator` needs a policy for the same role and
command. Under `FORCE ROW LEVEL SECURITY`, a grant with no policy is dead.
The negative run below shows it: the grant is there, yet reads return zero rows
silently and writes are rejected. This draft proposes the **29** missing
policies, each with its text, its reference in the document, the grant and
path it serves, and its results in both directions.

## Decisions already settled by the project owner (for v1.13's text)

1. **`membership_roles` and `tenant_modules` move into the manifest.** The
   `provisioner` sets `app.tenant_id` to the target tenant inside its own
   transaction. Its policies on tenant tables are
   `WITH CHECK (tenant_id = app.tenant_id)`; on the global identity tables
   (`persons`, `users`), `WITH CHECK (true)`.
2. **No `rls_exemptions` table.** The exemption list is a file in the
   repository, like the manifest, and it is Check 5's input. This changes the
   text of Check 5 in 3.6, which today reads
   `c.relname NOT IN (SELECT tbl FROM rls_exemptions)`.
3. **`tenants`:**
   ```sql
   tenants(id, name, status CHECK (status IN ('active', 'suspended')), created_at)
   ```
4. **`invitations.intended_scope_mode` belongs to T2 (the schema).** Its
   behavior belongs to T4. As tested:
   ```sql
   intended_scope_mode text NOT NULL CHECK (intended_scope_mode IN ('all', 'assigned'))  -- no default
   ```

## How it was tested

- **One transaction, rolled back.** It creates the relevant tables (with
  decisions 3 and 4), `ENABLE` + `FORCE` RLS on every table, the document's own
  policies on those tables **verbatim** (v1.12), the full 3.8 grants matrix as
  of v1.12, a fixture of two tenants (A = target, B = other) with users,
  memberships, roles, invitations and catalog rows, and then the proposed
  policies below.
- **Each case runs alone,** as its role, with only the context it names
  (`app.*` variables), inside a subtransaction that is **always rolled back**.
  No case can affect another. The result is recorded as `count=N` (a
  `SELECT count(*)`), `rows=N` (rows a write affected), or `error=SQLSTATE`.
  The expected result was written into each case before it ran.
- **Both directions for every policy:** the intended path succeeds, and the
  forbidden path fails. "Forbidden" means: another tenant, a missing context,
  a column outside the grant, or a role that must not gain anything from the
  policy. Where the document's principle is a silent zero rows (an update to
  another tenant's row), the expected result is `rows=0`, and the table says
  "by design".
- **The texts below are extracted mechanically from the file that was
  executed,** and each results table from that run's output. They are the
  tested texts, not a copy.

## The proposed policies

Naming: `<table>_<role>_<command>` for the new roles' policies, and descriptive
names in the document's own style for `app_user`. Every policy has an explicit
`FOR` and `TO` (3.1), and every context read is
`NULLIF(current_setting(…), '')::<type>` (3.1, 1.10).

### P1. `tenants_provisioner_insert`

- **Reference:** 4.4 (1, 3-a); owner decision 1
- **Grant it serves:** 3.8: provisioner INSERT on `tenants`
- **Path:** Bootstrap: create the tenant. The provisioner sets `app.tenant_id` to the new tenant's id first; `tenants` has no `tenant_id`, so the condition is on `id`.

```sql
CREATE POLICY tenants_provisioner_insert ON tenants
  FOR INSERT TO provisioner
  WITH CHECK (id = (SELECT NULLIF(current_setting('app.tenant_id', true), '')::uuid));
```

## Notes for the owner's review: choices this draft made, which are yours to confirm or change

1. **`user_password_credentials_provisioner_insert` uses `WITH CHECK (true)`.**
   Decision 1 names `persons` and `users` as the global tables. This table is
   global too (no `tenant_id`), so the draft extends the same rule to it.
2. **`membership_auth_tenant_read` does not enforce "admin".** 4.2 says
   "tenant-scoped visibility for an admin". The database has no context
   variable for "admin"; `can_manage_scope` is the only permission it resolves.
   So, as written, every member of the active tenant can read that tenant's
   `membership_auth` rows (provider and `provider_config`, the tenant's IdP
   reference). "Admin" would be enforced by the endpoint's permission, as for
   `membership_tenant_read`. The alternative is to leave this policy out until
   SSO arrives (SSO is out of scope for the proof, PROOF_SPEC §4) and keep only
   the self read.
3. **`invitations_insert` enforces spec item f in the database.** An invitation
   with `intended_scope_mode = 'all'` requires `app.can_manage_scope`, in the
   `WITH CHECK` itself. The spec says "verified at creation" without saying
   where. The draft puts it in the database, following 1.9's principle (no
   application-only protection of a sensitive surface). T4.7 then holds from
   direct SQL as well (case 59).
4. **Acceptance needs `app.tenant_id` before it can read the invitation.**
   `invitations_provisioner_select` is scoped to the target tenant, so the
   provisioner has to know the tenant **before** it looks the token up. The
   acceptance request therefore has to carry the tenant id, for example in the
   invitation link, next to the token. This is a T4 design point to settle in
   the text. (Rule 7 forbids taking *scope* variables from a request; this is
   the provisioner's target tenant, not a scope variable. It should still be
   stated explicitly.)
5. **`modules_read` and `permissions_read` name two roles in one policy**
   (`TO app_user, provisioner`). That is valid with an explicit `TO` and passes
   Check 4. The alternative is one policy per role, if the manifest should keep
   one role per policy.
6. **Updates to another tenant's rows give zero rows, not an error**
   (cases 25, 64). That is the document's "silent below". The acceptance and
   revocation paths put these writes under the rows-affected guard (3.5/5).
7. **`tenant_modules_provisioner_insert` serves a grant that neither path in
   4.4 uses.** 3.8 grants it and decision 1 puts the table in the manifest, so
   the draft covers it. Whether bootstrap enables modules is for T4 to state.
8. **No new policy chains.** The only proposed policy that reads another table
   is `membership_auth_self_read` → `memberships`, which 4.6 already declares
   ("app_user for their own membership"). Every other policy reads context
   variables only. Check 10 needs no new entries for this draft.
9. **The manifest in v1.13** would gain `membership_roles` and
   `tenant_modules` (decision 1). All the other tables here are already in it.

## An open question this draft does not solve: bootstrap cannot seed the new tenant's base roles

| # | What happens | Role | Expected | Actual |
|---|---|---|---|---|
| 76 | The provisioner inserts an `owner` role for the new tenant C | `provisioner` | `error=42501` | `error=42501` |

Bootstrap (4.4, 3-a) creates a tenant and its first member with the `owner`
role. But nothing that runs at that moment can create the new tenant's roles:
- **`provisioner`** has only SELECT on `roles` in 3.8, and nothing on
  `role_permissions`.
- **`migrator`** seeds the base roles, but only at migration time, not at
  runtime.
- **`app_user`** is blocked from system roles by `system_role_guard_insert`,
  and has no context at bootstrap anyway.

So `membership_roles_provisioner_insert` has no `owner` role to point at for a
new tenant (case 10 passes only because the fixture seeded tenant A's roles).
This needs a model decision, not a policy text. For example: grant
`provisioner` INSERT on `roles` and `role_permissions` with
`tenant_id = app.tenant_id` policies (`system_role_guard_insert` applies
`TO app_user`, so it would not block the provisioner), or some other seeding
mechanism.
