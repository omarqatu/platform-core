# Proposal for PLATFORM_CORE v1.13: the missing policy texts, bootstrap, and generated values

**Status:** the second draft, for the project owner's review. **Not built.** Nothing
here enters `src/` or `Migrations/` until v1.13 is issued.
**Base:** PLATFORM_CORE v1.12, PROOF_SPEC v1.1.
**Tested on:** PostgreSQL 18.6 (Debian 18.6-1.pgdg13+2), Npgsql.EntityFrameworkCore.PostgreSQL 10.0.3, .NET 10, 2026-09-24.

> **One open decision blocks the key text in v1.13:** with EF, a forgotten key or
> timestamp is **silent**, not loud (section "Open decision"). Everything else in this
> draft is ready to go into the document.

## Changes since the first draft (owner's review)

- **P23 (`membership_auth_tenant_read`) removed.** `membership_auth` keeps the self read
  only. A case confirms the active tenant alone now shows nothing.
- **`membership_roles`, `tenant_modules` and `role_permissions` join the manifest,** each
  listing `tenant_isolation` explicitly beside its provisioner policy.
- **Bootstrap:** the provisioner gets INSERT on `roles` and `role_permissions`
  (`tenant_id = app.tenant_id`). The role definitions come from two new global catalogs
  seeded by `migrator`, `role_templates` and `role_template_permissions`, which the
  provisioner alone can read. Four new policies. **Case 76 is now a full bootstrap of a new
  tenant, and it succeeds.**
- **Keys and generated values** (owner decision): every key comes from the application
  (`Guid.CreateVersion7()`), and every timestamp is set explicitly by it. No command uses
  `RETURNING`. No `DEFAULT` on any column in `public`, and `NOT NULL` with no default.
  `migrator`'s seeding writes `uuidv7()` explicitly.
- **Test 28 [W]:** the EF model has no `ValueGenerated` other than `Never`, and the
  database has no `DEFAULT` on any column in `public`. Both sides were run.
- **The bootstrap path through the real EF commands,** in a separate throwaway database.

## Decisions settled by the project owner (for v1.13's text)

1. **`membership_roles`, `tenant_modules`, `role_permissions` are in the manifest,** with
   `tenant_isolation` stated explicitly. The `provisioner` sets `app.tenant_id` to the target
   tenant inside its own transaction. Its policies on tenant tables are
   `WITH CHECK (tenant_id = app.tenant_id)`; on the global identity tables,
   `WITH CHECK (true)`.
2. **No `rls_exemptions` table.** The exemption list is a file in the repository, like the
   manifest, and it is Check 5's input.
3. **`tenants(id, name, status CHECK (status IN ('active', 'suspended')), created_at)`.**
4. **`invitations.intended_scope_mode`** is in the T2 schema (`NOT NULL`,
   `CHECK IN ('all', 'assigned')`, no default). Its behavior belongs to T4.
5. **Bootstrap seeds the new tenant's roles from global templates:**
   `role_templates(id, code, name_ar, name_en)` and
   `role_template_permissions(template_id, permission_id)`, seeded by `migrator` and read by
   the `provisioner` only. The provisioner has INSERT on `roles` and `role_permissions`.
6. **Keys and generated values come from the application.** No `RETURNING`, no `DEFAULT` in
   `public`, and Test 28 [W] as above.

## How it was tested

- **SQL harness: one transaction, rolled back.** It loads the schema of the relevant tables
  (with decisions 3–6: no `DEFAULT` anywhere), `ENABLE` + `FORCE` RLS on every table, the
  document's own policies on those tables **verbatim** (v1.12), the 3.8 grants matrix plus
  the bootstrap grants, the fixture (two tenants, with the template catalog seeded the way
  `migrator` would), and the proposed policies below.
- **Each case runs alone,** as its role, with only the context it names, inside a
  subtransaction that is **always rolled back**. The result is `count=N`, `rows=N`, or
  `error=SQLSTATE`, and the expected result was written into each case before it ran. Every
  key and timestamp is supplied explicitly (`uuidv7()` / `now()`), the SQL equivalent of the
  application supplying it.
- **Both directions for every policy:** the intended path succeeds, and the forbidden path
  fails (another tenant, a missing context, a column outside the grant, or a role that must
  gain nothing). Where the document's principle is a silent zero rows, the expected result
  is `rows=0`, marked "by design".
- **The bootstrap of tenant C** runs as the provisioner in the same transaction, with no
  `RETURNING`. Its outcome is then checked by the new owner as `app_user`.
- **EF harness: a separate database** (`v113_ef`) with the same schema, policies and
  fixture, created for the run and dropped after it. A console program runs the bootstrap
  and an assigned member's audit write through EF Core, and records every command EF sends.
- **The texts and tables below are extracted mechanically** from the files that were
  executed and from their output. After assembly, the SQL in this file was diffed against
  the executed file, and every result against the run.

## Summary

| Run | Pass | Fail | Total |
|---|---|---|---|
| SQL harness **with** the proposed policies | 99 | 0 | 99 |
| SQL harness **without** them (the document's policies only, same grants) | 51 | 48 | 99 |
| EF, compliant model (`ValueGenerated.Never`) | bootstrap committed; owner checks pass; assigned audit write succeeds; **0 RETURNING** | | |
| EF, compliant model, **key and timestamp forgotten** | **committed silently**, see "Open decision" | | |

**The negative run:** without the proposed policies, **41 of the 42 intended cases and
bootstrap outcomes fail**. The one that passes is an isolation check (tenant A does not see
C's roles), which passes trivially when nothing was created. The bootstrap itself stops at
its first statement: `new row violates row-level security policy for table "tenants"`.

**A silent failure the negative run exposed:** without read access to the templates, the
bootstrap's `INSERT … SELECT` statements (roles from templates, role permissions, the owner's
role) inserted **zero rows with no error** (`INSERT 0 0`). So every template-derived insert
in the bootstrap is a **critical write** under the rows-affected guard (3.5/5): the number
of roles must equal the number of templates. The EF harness does this with its
`Expect(...)` checks.

## The proposed policies

Naming: `<table>_<role>_<command>` for the new roles' policies, and descriptive names in the
document's own style for `app_user`. Every policy has an explicit `FOR` and `TO` (3.1), and
every context read is `NULLIF(current_setting(…), '')::<type>` (3.1, 1.10).

### P1. `tenants_provisioner_insert`

- **Reference:** 4.4 (1, 3-a); owner decision 1
- **Grant it serves:** 3.8: provisioner INSERT on `tenants`
- **Path:** Bootstrap: create the tenant. The provisioner sets `app.tenant_id` to the new tenant's id first; `tenants` has no `tenant_id`, so the condition is on `id`.

```sql
CREATE POLICY tenants_provisioner_insert ON tenants
  FOR INSERT TO provisioner
  WITH CHECK (id = (SELECT NULLIF(current_setting('app.tenant_id', true), '')::uuid));
```

### Noncompliant model: two properties generated by the database, every value still set by the application

The model: `membership_scope.id` with `HasDefaultValueSql("uuidv7()")`, and `audit_log.created_at` with `HasDefaultValueSql("now()")`, both `ValueGeneratedOnAdd`. Test 28's model check flags them: `audit_log.created_at = OnAdd, membership_scope.id = OnAdd`. The run then committed like the compliant one, with 0 `RETURNING` (see below for why).

**Why the noncompliant model did not fail when every value was set:** EF sends a value it
was given even for a property configured `ValueGeneratedOnAdd`. It omits the column and
asks for it back with `RETURNING` only when the property still holds the CLR default
(`Guid.Empty`, `DateTime.MinValue`). So a database-generated configuration is a latent
risk that fires exactly when a value is forgotten. That is what the next section tests.

## ⚠️ Open decision: with EF, a forgotten key or timestamp is silent, not loud

The key decision rests on "`NOT NULL` with no default: forgetting is a loud error." That
holds for hand-written SQL (Test 28, database side: `23502`). **With EF it does not.** The
same bootstrap and audit write, with `membership_scope.id` and `audit_log.created_at` left
unset on purpose:

| Model | What EF sent | Result |
|---|---|---|
| **Compliant** (`ValueGenerated.Never`, the owner's decision) | `Guid.Empty` and `0001-01-01` as ordinary values, 0 `RETURNING` | **Committed silently.** In the database afterwards: 1 `membership_scope` row whose key is `00000000-0000-0000-0000-000000000000`, and 2 `audit_log` rows dated year 1 |
| Noncompliant (generated by the database) | the columns omitted, 2 `RETURNING` | Loud: the bootstrap failed with `42501: permission denied for table audit_log`, and the assigned write with `42501: new row violates row-level security policy for table "audit_log"` |

So, as things stand, the compliant model makes forgetting **silent**, which is the class of
failure the document hunts down. The next key-less insert into the same table would then hit
a unique violation (the nil uuid again), but a forgotten timestamp would never be noticed.
Foreign keys and `tenant_id` are not affected: a forgotten one is caught by the composite FK
or by the tenant's `WITH CHECK`.

**Options (the owner's decision; none of them has been run yet):**

1. **Loud above:** a `SavingChanges` interceptor in Core, next to the transaction
   interceptor, that throws when an `Added` entity has a key equal to `Guid.Empty` or a
   non-nullable `DateTime` equal to `default`. Test 28 [W] would then also require this
   interceptor to be registered and to be seen failing once.
2. **Loud below:** `CHECK` constraints in the database: every key `<> '00000000-…'`, and
   every timestamp later than a fixed floor. That covers every writer, not just EF, and a
   check (a new Check, or part of Test 28) would enforce its presence on every column.
3. **Both.**

Whichever is chosen, it will be run in isolation before v1.13 is issued, both directions,
through the real EF commands.

## Notes for the owner's review

1. **`user_password_credentials_provisioner_insert` uses `WITH CHECK (true)`.** Decision 1
   names `persons` and `users` as the global tables. This table is global too (no
   `tenant_id`), so the draft extends the same rule to it.
2. **`invitations_insert` enforces spec item f in the database.** An invitation with
   `intended_scope_mode = 'all'` requires `app.can_manage_scope` in the `WITH CHECK`
   itself, following 1.9's principle (no application-only protection of a sensitive
   surface). T4.7 then holds from direct SQL as well.
3. **Acceptance needs `app.tenant_id` before it can read the invitation.**
   `invitations_provisioner_select` is scoped to the target tenant, so the acceptance
   request has to carry the tenant id (for example in the invitation link, next to the
   token). This is a T4 design point to state in the text. It is the provisioner's target
   tenant, not a scope variable (rule 7).
4. **`modules_read` and `permissions_read` name two roles in one policy**
   (`TO app_user, provisioner`). That is valid with an explicit `TO` and passes Check 4. The
   alternative is one policy per role.
5. **Updates to another tenant's rows give zero rows, not an error** (invitations). That is
   "silent below". The acceptance and revocation paths put these writes under the
   rows-affected guard.
6. **`tenant_modules_provisioner_insert` serves a grant that neither path in 4.4 uses.**
   Whether bootstrap enables modules is for T4 to state.
7. **No new policy chains.** The only proposed policy that reads another table is
   `membership_auth_self_read` → `memberships`, which 4.6 already declares. Check 10 needs
   no new entries.
8. **The bootstrap's template-derived inserts are critical writes.** Without read access
   they insert zero rows silently (the negative run), so the path checks rows-affected
   against the number of templates.
